## 本机运行与开发

需要 Node.js 22.13+（建议 24）及单独准备的 PostgreSQL 18 数据库。应用账号需有目标数据库的建表权限。Windows 命令统一用 PowerShell 7。

```powershell
npm ci --omit=dev --ignore-scripts
$env:DATABASE_URL = 'postgresql://labos@127.0.0.1:5432/labos_development'
npm run check
npm run dev
```

连接地址须替换为自己创建的开发数据库，并按该 PostgreSQL 实例的认证配置提供凭据。不要把真实连接口令提交到 Git。`config/.env.example` 只供参考，普通 Node 启动不会自动加载它。连接未配置或不可用时应用报错，不回退为新的 SQLite 空库。

开发默认地址为 `http://127.0.0.1:3001`，附件和日志放在 `var/development/0.9.4/`；数据库位置由 `DATABASE_URL` 决定。Git 分支或运行目录不会自动隔离 PostgreSQL，开发、测试和日常使用必须连接不同数据库。`npm start` 默认端口 3000，附件和日志默认放在 `var/`。

空数据库首次打开网页时设置管理员账号和密码，密码至少 8 位且需确认；没有默认密码。已有用户时不会开放首次设置。

测试另需专用 PostgreSQL 实例及可创建临时数据库的测试账号：

```powershell
$env:LABOS_TEST_DATABASE_URL = 'postgresql://labos_test@127.0.0.1:5432/postgres'
npm test
```

测试按用例创建和清理隔离数据库，缓存放在 `artifacts/cache/0.9.4/`。该变量必须指向专用测试实例；不得填日常业务数据库。测试与容器、真实浏览器及群晖验收的边界见[开发说明](docs/DEVELOPMENT.md)和[版本说明](docs/CHANGELOG.md)。

## 物资信息与库存

“物资主档”就是同种物资的标准信息，在页面中称为**物资信息库**，保存编码、名称、规格、单位、分类和管理方式。它不代表已经有库存；库存数量由期初、验收、调整和领用流水累计。相同名称但规格或单位不同的物资分别保留。

申报时先选择区域和仓库，按中文名称或规格检索，所选范围有库存的物资优先显示；已有物资用完后仍复用原信息，不因零库存重复建档。确认没有匹配项时可以填写新物资并提交，验收前由具有维护权限的管理员确认建档或关联已有信息。0.7.0 页面将程序编码显示为只读，后端自动分配；中文名称、规格和单位共同确定身份，同名不同规格不混合。已提交单的关联仍由物资管理员填写原因修订，保留原提交与修改历史。

物资信息库支持下载 XLSX 模板、导入和导出。**导入物资信息只建立标准信息，不增加库存、不生成实物条码。** 带数量、金额和存放位置的旧有实物，从“期初库存”或期初关闭后的“存量补录”导入草稿，核对并确认入库后才记库存；补录必须原因并保留流水。逐件管理物资按实际入库整数数量生成一瓶／一件一个固定码。

0.7.0 模板使用物资、分类、区域、仓库和管理方式的中文引用列表；导入错误返回工作表、实际行列、字段、输入值与原因，并在原表单中逐条显示。每类参考列表最多带 5000 条，本次导出涉及的数据优先；超过列表容量时允许手填已有中文名称，导入仍由服务端核对身份与权限，不限制整个信息库只能有 5000 条。物资名称、规格、单位须组合匹配同一物资。

仅库存与物资信息库要求导出回导：信息库原样回导复用已有信息，库存按批次复制到草稿，核对后才确认入库；再次导入库存并非自动去重或恢复历史账。申报、验收和领用 Excel 保持历史报表，不回放业务动作。导入先完整校验，错误整批不写；工作簿解析后再次验证登录与操作权限。

物资页保留“申报 / 验收 / 库存 / 期初库存 / 领用”五个入口。全员可建申报单、添加本人草稿明细；提交、验收、已提交单修订及领用发放需要 **MATERIAL（物资管理员）** 角色及对应动作权限，只有 ADMIN 角色不能代办。分类、归属区域和物资信息由有对应维护权限的 ADMIN/MATERIAL 管理。

库存按物资、仓库和区域合并，保留批次、有效期、存放位置和来源；领用由人员申请，物资管理员确认发放才扣库存。逐件管理发放时选择具体在库实物；申请不预占库存，不支持开瓶余量或同一申请部分发放。接口与 Excel 规则见[物资 API](docs/MATERIAL_API.md)。

## Docker 与群晖

两份 YML **任选一份**，都包含初始化、PostgreSQL 18、应用和 HTTPS 代理四个服务，无需另外准备 `.env` 或 `Caddyfile`。从0.9.4 Release下载同版本配套文件；在线应用镜像为`ghcr.io/hotll233/labmg:0.9.4`，本地三镜像包使用`labos:0.9.4`：

| 部署方式 | 文件 | 镜像来源 |
| --- | --- | --- |
| 在线拉取 | [0.9.4 docker-compose.yml](https://github.com/HotLL233/labmg/releases/download/v0.9.4/docker-compose.yml) | 应用从 GHCR 拉取，PostgreSQL 和 Caddy 使用官方镜像 |
| 本地导入 | [0.9.4 docker-compose.local.yml](https://github.com/HotLL233/labmg/releases/download/v0.9.4/docker-compose.local.yml) | 先导入本架构 TAR 内的三个镜像，所有服务禁止拉取 |

0.9.4的[在线YML](deploy/docker-compose.yml)与[本地YML](deploy/docker-compose.local.yml)默认使用`LABOS_HTTPS_HOST=auto`：只有一次性`labos-init`使用宿主机网络，识别一个主局域网IPv4，写入`runtime/https-config/Caddyfile`，代理只读加载该配置。无合适地址或多网卡无法确定时明确失败；可在`labos-init`内手动指定实际IPv4或主机名，不带协议、端口或路径。空值、`CHANGE_ME`及`0.0.0.0`均按自动识别处理，手机仍须打开日志显示的实际HTTPS地址并信任根证书。旧0.9.2的手填IP步骤仅适用于旧配套文件。

首次安装用独立目录，不指向 PG17／SQLite 旧库；已部署 PG18 的同项目更新保留原数据与证书目录，不重新初始化。本次不提供 PostgreSQL 主版本迁移。

数据保存在 **YML 同目录的 `runtime/`**：`postgres/18/docker/` 是 PG18 数据，`uploads/` 是附件，`secrets/postgres-password` 是自动生成的数据库口令，`https-config/Caddyfile`是0.9.4初始化生成的代理配置。HTTPS证书继续保存在旁边的`https/data/`；群晖首次部署先创建`runtime/`与`https/`父目录。后续同一 PG18 项目更新时保留完整 `runtime/`、`https/`、项目和 UID/GID。备份及操作步骤见[群晖部署](docs/SYNOLOGY.md)。

每架构离线 TAR 包含应用、PostgreSQL 18 和 Caddy 三个镜像；导入一份后使用本地 YML，服务无需联网拉取镜像。发布状态与实际验证以 Release 为准。

## 打印与手机扫码

网页标签只打印二维码和基础信息，实体纸宽×走纸长与内容0°／90°旋转分开设置，支持布局、毫米偏移与模板JSON导入导出；可选起止张、试打首张并打开系统打印窗口。当前38.5×30.5mm纸按纸卷宽38.5mm、走纸长30.5mm设置，旋转内容不交换纸张尺寸。重印复用原单件编号，不增加库存或流水。旧BarTender后台任务须在原Windows电脑停止并移除，原指南仅作历史记录。纸张和驱动校准见[标签打印说明](docs/LABEL_PRINTING.md)。

0.9.2的“标签模板”支持拖拽字段，预览可选100%／150%／200%／300%，默认200%；选中元素后在预览内使用方向键沿实体纸面移动0.1mm，Shift为1mm。2mm留白虚线只作编辑参考，尺寸和字号仍通过数值修改，缩放不改变输出尺寸。沿用当前浏览器、当前访问地址的schema1模板及JSON导入导出；拖拽和键盘移动到边界停止，手填越界及实际文字溢出仍会拒绝。2026-10-22用户确认此前提供的38.5×30.5mm两方向留白JSON模板均正常打印；该反馈只覆盖这两份模板，不代表本轮新设计器或所有纸型已验收。

0.9.4沿用0.9.3打印页，将尺寸、内容方向与偏移收进默认折叠的“纸张与校准”，将模板来源、驱动与PDF长说明收进“打印帮助”。起止张及“试打首张／系统打印／保存 PDF／保存设置”始终可见，状态和错误显示在折叠区外，工具区随页面滚动。没有模板、模板无效或存储不可读时仍从60×40mm示例载入初始布局，不覆盖原设置；展开帮助查看来源，按实际纸卷修改并保存。“保存 PDF”仍打开系统窗口，由用户选择浏览器“另存为 PDF”，不自动导出文件；Windows“Microsoft Print to PDF”是另一输出路径。0.9.3期间标签Node28/28及真实隔离Edge188项、6份单页PDF／6图通过，本轮沿用相同界面源文件的有限证据，未重跑该浏览器专项，不代替原生窗口或USB试打。

手机实时相机需要受信任的 HTTPS、系统与浏览器相机授权；普通群晖 IP 的 HTTP 地址保留拍照／选图和手输。现有0.9.2 NAS已于2026-10-22修正代理地址并恢复严格可信HTTPS，应用、数据库与CA保持原样；0.9.4自动识别尚未部署到该NAS，手机相机及USB打印仍待现场确认。证书安装和本次恢复结果见[扫码 HTTPS 配置](docs/SCANNING_HTTPS.md)。

## 目录与版本管理

| 路径 | 内容 |
| --- | --- |
| `src/` | PostgreSQL 数据库模块、服务端和静态前端 |
| `scripts/` | 检查和打包脚本 |
| `tests/` | 真实 PostgreSQL 隔离回归、前端与打包检查 |
| `config/`、`deploy/` | 本地环境示例、Dockerfile 与正式 Compose |
| `docs/` | 记忆、开发记录、版本说明与操作文档 |
| `var/` | 本地附件与日志，不提交 |
| `runtime/` | Compose 项目旁的数据库、附件和秘密文件，不提交 |
| `artifacts/releases/<version>/` | 冻结交付产物，不提交 |
| `artifacts/cache/<version>/` | 按版本隔离的构建与测试缓存，不提交 |

`main` 保存发布基线，`develop` 与 `feature/*` 用于开发；标签与旧产物保留。`npm run package:zip` 和 `npm run package:docker` 使用实际包版本生成产物；源码冻结后补文档不重打归档或移动旧标签。Docker 打包需要运行中的 Linux Docker 引擎与 Buildx。

开发约定见 [DEVELOPMENT](docs/DEVELOPMENT.md)，长期记录集中在 [MEMORY](docs/MEMORY.md)、[HISTORY](docs/HISTORY.md) 和同一份 [CHANGELOG](docs/CHANGELOG.md)。

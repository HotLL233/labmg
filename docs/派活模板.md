# 派活模板

> 给人类看的，AI 不用读。每次派活复制中间那段，填空后发出去。

---

## 复制这段

```
## 任务
<一句话说清改什么>

## 范围
- 只许改：<文件路径，越具体越好>
- 不许碰：其它任何文件

## 验收
- npm run verify 必须 PASS
- <一条可断言的结论，例如：1440 宽下 .pill 背景为 #eef1f5>

## 交付
贴 npm run verify 原文（不要概括）+ 改动的 文件:行

## 硬规矩
1. 先读 docs/CONTEXT.md，不要通读 docs/MEMORY.md / HISTORY.md
2. 只在 src/ scripts/ tests/ docs/ 里搜，不要从根目录全量搜
3. 只做上面这一件，不要顺手改别的
4. 不确定就停下来问
```

---

## 三种派法对比

| 派法 | 结果 |
| --- | --- |
| ❌「把 `docs/UI_整改方案.md` 全部整改一遍」 | 一次改 24 条、5 个文件，样式互相覆盖，改到第 8 条崩，前功尽弃 |
| ❌「把界面优化一下」 | 范围没有边界，它会先花 10 分钟猜你想干嘛，再改一堆你没要的 |
| ❌「看看哪里有问题，顺手修好」 | 没有验收标准，它改完也不知道对不对，只能反复试探 |
| ✅「只改 `tokens.css` 的 `--fs-panel` 从 18px 到 20px，改完跑 `npm run verify` 贴输出」 | 一条、一处、一个验证，5 分钟出结果 |

## 三条判断标准

1. **一个任务只对应一处改动。** 要改 5 处就派 5 次，宁可多轮，不要一轮崩。
2. **验收必须是命令能判定的。** 「看起来好多了」不算验收，「`npm run verify` PASS」才算。
3. **范围写死文件名。** 「优化前端」≠ 范围，「只改 `responsive.css` 第 40–90 行」= 范围。

## 任务大了怎么办

拆成有依赖顺序的子任务，一次一个，前一个 PASS 了再派下一个：

```
第 1 轮：只改变量定义（tokens.css），verify PASS
第 2 轮：只改一个页面的样式引用，verify PASS
第 3 轮：只改另一个页面，verify PASS
```

反过来「一次全改完」看着省事，实际每轮都在等它重试和回滚。

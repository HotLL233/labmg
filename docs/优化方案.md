## 本轮实施核对（2026-10-22，0.11.0，T1–T4／批次C）

- 0.10.1已经作为申报验收解耦版本公开，不能再用下方预排的0.10.1发布批次C。用户要求完成本轮包括UI，实际新版本定为0.11.0，独立feature/v0.11.0-material-ui-inventory；旧版本和标签不改。D/E/F仍是后续路线图，不把原预排号当成真实发布。

- C的厂家聚合仅用于新可选GET /stock/batches?detail=1；原GET /stock及默认批次、位置和二维码身份均保留。直接对全部正负流水按厂家GROUP BY会把跨厂家领用错误归给空厂家，因此采用明细分配：数量型新负流水在原事务内写快照manufacturerAllocations，优先填写的厂家再按入库顺序；历史无分配元数据的负流水只按此展示政策重放，不回填历史厂家，未知入库厂家仍显示“—”。逐件型按实际单件来源追溯。
- 每批次厂家余额之和须等于旧批次余额；金额沿用整批均价，展示分摊补尾差，不宣称厂家独立成本。厂家规范化／历史建议、批次备注、物资备注及Excel兼容旧模板一并接入；不改已应用0003迁移，备份保持schema6并严格校验新元数据。
- 真实验证和发布结果按本轮MEMORY／HISTORY／CHANGELOG后续实测记录，不以计划或旧版计数代替。本轮不自动升级NAS或验证USB打印。

## 3. 施工任务

六个批次，按依赖顺序。**批次 A 可选，批次 B 必须先做**。批次 D（退库）只依赖 B0 的迁移基建，不依赖 B1/B2 的业务改动，可以提前插入或与 C 并行。

### 批次 A（`0.9.5`，可选，纯性能与安全，零业务改动）

不依赖任何迁移，可独立发布、独立回滚。**如果只做一件事，做 A3。**

| 编号 | 任务 | 改法 | 验收 |
| --- | --- | --- | --- |
| A1 | 补索引 | `schema.js` 追加 `CREATE INDEX IF NOT EXISTS`：`records(module, created_at)`、`records(updated_at)`、`audit_logs(created_at)`、`files(record_id)`、`sessions(expires_at)` | 万条 fixture 下 `EXPLAIN (ANALYZE, BUFFERS)` 前后对比，Seq Scan → Index Scan |
| A2 | 去函数包裹 | `server.js:98,175,211` 把 `labos_date(created_at)>=labos_date(?)` 改为先按 `YYYY-MM-DD` 校验入参、再直接比较 `created_at>=?`（列是文本，字典序即时间序） | 现有日期筛选测试 + 非法日期用例返回 400 |
| A3 | 压缩与缓存 | Caddyfile 模板加 `encode zstd gzip`；静态响应加 `ETag`（size+mtime）与 `Cache-Control: no-cache`，命中返 304；`/vendor/*` 用 `immutable` | 浏览器网络面板：首屏传输体积下降、二次访问 304 |
| A4 | SQL 编译缓存 | `database.js:117` 用 `Map` 缓存 `compileSql(sql)` 与 returningId 版本，键为原 SQL 串，上限 500 条 | 215 项测试全绿 |
| A5 | 安全补丁 | ①登录 Origin 校验（复用 `server.js:104` 逻辑）；②token 哈希入库（sha256）；③登录轮换 token；④按 `X-Forwarded-Proto` 或直连 TLS 加 `Secure`；⑤启动清理过期会话；⑥加 CSP/nosniff/Referrer-Policy/Frame-Options | 新增安全用例；登录与权限回归全绿 |
| A6 | 登录限速 | 进程内 `Map`，按"账号+IP"双键，失败 5 次锁 5 分钟，成功清零，只挡 `/api/auth/login` | 连续失败用例 + 正常登录不受影响 |

**A4 的 `prepare()` 注意**：`compileSql` 是纯函数，缓存安全；但缓存要放在 `prepare()` 外层，不要改 `compileSql` 本身。

### 批次 B（`0.10.0`，核心：申报模糊 + 验收完善）

**目标**：申报时不碰主档，验收时才完善。这是用户最核心的诉求（R13）。

#### B0 迁移基建（必须先做，其它批次都依赖）

现在是 `CREATE TABLE IF NOT EXISTS` + `server.js:37-42` 的两处手写补丁，撑不住加列。

要求：**自写，不引依赖**。

```
scripts/migrate.js
  - 启动时（或 npm run migrate）扫描 migrations/NNNN-*.sql
  - 表 schema_migrations(version TEXT PRIMARY KEY, applied_at TEXT NOT NULL)
  - 按版本号升序执行未应用的 SQL，每条在独立事务里跑
  - 已应用的跳过；失败即停并打印文件与错误，不自动回滚后续
  - 兼容：现有 2 处手写补丁已写入 schema_migrations 的记录，把它们的版本号登记进 migrations/ 的同名文件（内容为空 + 注释"已由 legacy 补丁应用"）或直接从已应用集合中跳过
```

验收：**两条路径都要过**——① 空库从零建到最新；② 从 `0.9.4` 生产库原地升级，不丢数据、不报错。

#### B1 申报阶段解耦（后端）

| 位置 | 改法 |
| --- | --- |
| `materials.js:379-392` `lineInput()` | 删掉 `SELECT * FROM material_catalog ORDER BY id` 的全表读取、`coded`/`matches` 自动匹配，以及两条 `conflict`（`该编码对应的名称、规格或单位不同`、`存在多个相同物资信息，请明确选择编码`）。改为：`input.catalogId` 有值 → 校验主档存在后关联；无值 → `catalog_id=NULL`，`name/spec/unit` 用用户原文 |

保留不变：`code` 仍可自由填写；`category_id`、`region_id`、`warehouse`、`qty_m` 校验全不动。

**副作用检查**：`lineInput` 末尾 `unitQuantity(master || {tracking_mode:'quantity'}, ...)` 已能处理无 master 的情况，不用改。

在 `materials.js:803`（`if (!line.catalog_id) conflict(...)`）**之前**插入解析逻辑：

### 批次 D（`0.10.2`，领用退库：被领用的物资可再次入库）

**需求（R14，用户原话）**：「被领用的物资也可再次入库」。

**现状核查结论**：库存能加回去，但**加回去的东西不是原来那件**。

| 事实 | 证据 | 后果 |
| --- | --- | --- |
| 已有 `POST /stock/adjustments` 可手工调增库存 | `materials.js:1546,1562`，`type='adjustment'` | 能凑合，但不关联领用单，对不上账 |
| 调增单件追踪物资时**会生成全新单件码** | `addMovement:461` `if (single && data.qty_m > 0) await generateUnits(...)` | 退回的那瓶换了编号，**贴在瓶上的原标签直接作废**，扫码查不到 |
| 流水类型没有"退库" | `schema.js:144` `CHECK(type IN ('opening','receipt','reversal','adjustment','issue'))` | 无法按类型统计退库 |
| 领用流水 `source_key` 唯一 | `materials.js:727` `issue:${row.id}` | 一张领用单只能产生一条流水，多次退库必须另起键 |
| 单件码状态约束 | `schema.js:197-199`：`in_stock` 要求 `exit_movement_id IS NULL` | 退库必须同时清 `exit_movement_id`，否则约束不通过 |
| `ensureBalance` 只拦负数 | `materials.js:439-449` `if (quantity<0||amount<0) conflict(...)` | 加库存不受限，退库天然通过 |

#### D1 迁移（`0004-issue-return.sql`）

放宽流水类型约束，增加 `return`：

```sql
-- 约束名由 PostgreSQL 自动生成，先按 information_schema 取真实名再 DROP，不要硬写
ALTER TABLE material_stock_movements DROP CONSTRAINT IF EXISTS material_stock_movements_type_check;
ALTER TABLE material_stock_movements ADD CONSTRAINT material_stock_movements_type_check
  CHECK (type IN ('opening','receipt','reversal','adjustment','issue','return'));
```

这是**放宽**而不是收紧：旧代码写入的 type 全是新集合的子集，所以旧版本代码在新库上仍可运行，回滚安全。这是本方案里唯一一处非纯加法迁移，理由必须写进 CHANGELOG。

`material_issues` **不加字段**：已退量用流水聚合算（`source_key LIKE 'return:<id>:%'`），避免冗余与不一致。1 万条以内聚合开销可忽略。

#### D2 后端：`POST /issues/:id/returns`

权限 `materials.issue.write`（与发放同权）。请求体：`{ quantity, reason, unitIds? | unitCodes?, version }`。

事务内顺序：

| 步 | 动作 | 要点 |
| --- | --- | --- |
| 1 | 校验 `issue.status === 'issued'` | 未发放、已驳回、已取消的都不能退 |
| 2 | 算已退量与可退量 | `issue.qty_m - SUM(return 流水)`，聚合时校验不超安全整数 |
| 3 | 拒绝超退 | `quantity > 可退量` → `conflict('退库数量超过可退数量')` |
| 4 | 算退库金额 | 按剩余金额比例退，**最后一次退完必须刚好归零**：`min(剩余金额, round(issue金额 × quantity / issue数量))`，避免多次部分退产生舍入残值 |
| 5 | 写流水 | `type='return'`、`qty_m=+quantity`、`amount_cents=+金额`、`source_key='return:<issueId>:<seq>'`、`receipt_id=null`、`reason` 必填、批次/效期/位置沿用原领用单 |
| 6 | 单件码回库 | `UPDATE material_stock_units SET status='in_stock', exit_movement_id=NULL WHERE id IN (...)`。**只允许退原领用单发放出去的那些码**，且只允许 `status='issued'` 的；`void`（已作废）拒绝 |
| 7 | 审计 | `log(user,'RETURN_ISSUE','material_issues', id, ...)`，把退回的单件码列表写进审计，弥补 `exit_movement_id` 清空后的溯源需求 |

## 4. 迁移规范

- 文件命名：`migrations/0001-xxx.sql`、`0002-...`，四位数、单调递增、**已应用的文件不许再改**。
- 只做加法：`ADD COLUMN ... DEFAULT ...`、`CREATE INDEX IF NOT EXISTS`、`INSERT` 配置行。
- **唯一允许的例外：放宽 CHECK 约束**（批次 D 需要给流水类型加 `return`）。判据是"新约束是旧约束的超集"，旧代码写入的值仍合法，因此旧版本在新库上照跑、回滚安全。收紧约束一律不做。这类迁移必须在 `docs/CHANGELOG.md` 里单独写一行说明。
- 加列原则：`TEXT NOT NULL DEFAULT ''` 或 `BIGINT`（可空）。**不写 `NOT NULL` 无默认值**，否则生产库现有行无法满足。
- 不回填历史 `snapshot` JSON。老流水没有 `manufacturer`，展示为空，**不推测**。
- 每条迁移必须能在已有数据的库上跑，且旧代码在新库上仍可运行（回滚安全的前提）。
- 改完后 `npm run check` + `npm test` 全绿才算完成。

# 物资流程与页面简化方案

日期：2026-10-26。核对基线：0.13.1 发布后文档提交 `0f99965`。本轮为**方案与离线交互原型**，未改正式业务页面、API、数据库、版本、部署 YML 或镜像。

参考：[可交互 HTML](prototypes/material-workflow-simple.html)，可直接用浏览器打开。全部记录为合成示例，验收只改变页面内存，不连接实际库存。用户已确认：**实付金额直接在验收表内填写，填好后点击入库**。

2026-10-26 补充：用户明确“打印申报单，每次到货在纸上勾选，上传本次到货清单，直到整单到齐”。本次补充将**厂家核对移至常驻验收区**，替代初稿将厂家藏在差异区的建议；采用**分次到货清单、同次版本替换**，不是整张申报单只留最后一次清单。详细规则见第9节。

## 1. 改什么，为什么

验收应围绕一张申报单连续办理，默认沿用原单资料与剩余待验数量。到货一致时只填本次合格总额并核对位置，即可在当前行验收入库；有差异才展开这一行。物资管理常驻业务入口只保留“申报、验收、库存”，低频资料与配置通过右侧“物资设置”进入。

当前繁琐主要来自任务结构，不是字体或留白本身：

| 当前实现 | 问题 | 改法 |
| --- | --- | --- |
| `material.js` 的 `shell()` 并列七个入口 | 日常业务、辅助操作、资料维护混在同级 | 三个业务页签；设置使用独立工具按钮 |
| `acceptanceRows()` 按物资明细分页 | 同一张申报单被拆散，用户反复确认来源 | 左侧按申报单查找，右侧完整显示所选申报单 |
| `formItem()` 为每条验收打开完整表单 | 正常收货也要逐个穿过多字段页面 | 金额和位置行内处理，差异按需展开 |
| `workspace.js` 的 `show()` 将各种 dialog 统一铺满工作区 | 改一项与办理整单具有相同的跳转成本 | 短操作在原位，复杂单据才进入完整工作区 |
| 同一单元格重复身份、分类、区域、版本和操作 | 表格行变高，实际待办被挤压 | 名称主显、编码辅显；单据共有资料放单头，历史与说明按需查看 |

不继续缩小字号来塞内容。沿用施工卡的 14px 正文、13px 标签、12px 说明、七档字号与三档行高；桌面控件至少 36px，触屏至少 44px。表格沿用屏幕 8×12px 内边距与竖线，手机由同一份 DOM 重排。

## 2. 三个业务入口与物资设置

| 入口 | 默认呈现 | 次要功能放哪里 |
| --- | --- | --- |
| 申报 | 申报单记录表；选择后在同一工作区查看或录入明细 | 新建、草稿协作、提交、修订、附件、Excel 导出保留；增加带原单二维码的打印／下载核对单，已提交单可直接“去验收” |
| 验收 | 待验收申报单列表＋当前整单验收清单 | 常驻厂家核对、上传本次到货清单；扫码入库属于本页，历次到货资料、验收事件、拒收、结案、冲正按需展开 |
| 库存 | 库存记录表，物资名称优先；保留现有七列台账 | 领用申请／待发放／记录、期初／补录、库存流水为本页内部功能；行内提供领用、位置、单件码与打印 |
| 物资设置（独立工具按钮） | 分区显示，不再是一张混合长表单 | 物资信息库、分类、区域、库位、编号规则、标签模板；原台账放“历史资料” |

“物资信息库”保存物资基础资料，不等于实际库存。进入设置不应改变查询权限：普通人员仍可查询其有权查看的物资，维护按钮按原权限显示；不能因统一入口而将资料查询变成管理员专属。

申报页和验收页共用同一张申报单及明细，不复制成第二套采购单。原来“期初／补录”“领用”等入口只是移入库存页，并不删除这些功能，也不改变期初关闭、补录原因或管理员发放规则。

## 3. 验收页布局

```text
物资管理                 申报  [验收]  库存           物资设置
待验收／部分验收／全部历史     搜索单号、主题或物资       扫码入库
┌ 申报单列表 ──────────┬ 当前申报单：单号、主题、进度 ────────────┐
│ 单号、主题、日期      │ 物资名称 / 规格  待验  本次合格  实付总额  位置  操作 │
│ 待处理项数、状态      │ 乙醇 / 500mL     6      6       [金额] [库位] [验收] │
│ 点击后保留列表位置    │ 离心管 / 15mL   10    [6]       [金额] [库位] [调整] │
│                      │    常驻厂家核对；展开本行：拒收、批号、效期、差异原因 │
├─────────────────────┴─────────────────────────────────────┤
│ 已选 N 项 / 本次合格数量 / 金额     验收选中项     验收整单待验项 │
└───────────────────────────────────────────────────────────┘
```

桌面左栏紧凑显示申报单，右侧为整单明细；共有申报人、区域等在单头或摘要显示，混合区域／仓库单仍在行上明确区别。长清单只让正文区域滚动，单头、错误提示与操作条保持可达。

手机同一 DOM 依次呈现申报单选择和明细卡片，提供“返回申报单列表”锚点；金额与操作不塞进过宽横表。桌面尽量同屏，手机、低高度、放大和长内容允许必要纵向滑动，不能裁掉字段、提示或按钮。

## 4. 正常与差异分开处理

### 4.1 到货一致

1. 选一张已提交申报单，显示整单物资，不再逐条找来源。
2. 默认本次合格数量为**当前剩余待验数量**，沿用已确认的物资身份、区域与仓库。部分验收后不能再次默认原申报总量。
3. 直接填写“本次合格总额（元）”，核对实际存放位置。位置可选择已有中文库位；库存已存在的位置不能被猜测值静默覆盖。
4. 在常驻区对照“申报厂家／实到厂家”，相符时沿用；不相符填写实际厂家和差异原因。点击验收即明确表示已核对，不另加一轮重复确认窗口。
5. 点本行“验收”，或选择本次已到货的多项物资点“验收选中项”。金额、厂家及本次操作触发的必填项齐全时直接入账，不再弹一张重复填写的确认表。一次多项确认形成同一到货登记，避免一份到货清单需要逐物资重复上传。
6. 成功后留在原申报单，更新剩余量、进度和库存，显示“打印本次标签”和“上传本次到货清单”，不需要再次到历史里查找。附件可事后补传，资料待补不等于未入账。

没有实际金额的行保持空值并提示“请填写本次合格总额”，不能取旧库存价、默认 0 或把预计价当实付金额。金额为合格物资的本次总额，不含拒收部分；真正零元入库仍须填写原因。金额可见性继续按独立权限控制。

位置沿用当前可选合同：省略时保留已有位置；显式填写时校验位置版本，实际变更另需库位维护权限。不因本方案将位置一律升级为必填，也不让缺少库位维护权的验收人员被迫修改位置才能入库。

### 4.2 数量、质量或批次有差异

点击本行“调整”，在该行下方展开拒收数量及原因、批号、有效期、厂家差异原因和备注；本次合格数量与实到厂家常驻。实际有必填错误时自动展开并定位。

| 情形 | 行为 |
| --- | --- |
| 部分到货 | 修改本次合格数量，其余继续待验；未到货行不勾选 |
| 拒收 | 填拒收数量与原因；拒收不计入合格库存，不自动取消后续需求 |
| 短缺不再补货 | 单独使用“差缺结案”，说明原因；不因本次数量少而自动结案 |
| 实物不同于原申报身份 | 保留原申报，提示先按权限修订原单；不能借验收调整静默换物资、单位、区域或仓库 |
| 一行尚未关联物资资料 | 就地展开“匹配已有／建立物资资料”；建档失败则本次验收不入账 |
| 已经入账的错误 | 从只读历史发起有原因的冲正；不能直接编辑历史数量和金额 |

例如申报 10 件，本次合格 6、拒收 2，仍有 **4 件待合格验收或结案**，不是 2 件。原申报量始终保留为 10。已有任何验收、拒收或结案事件后，沿用当前身份锁定规则，冲正也不解除身份锁定。

### 4.3 多行入库与失败处理

“验收整单待验项”属于明确的批量动作：显示待处理项数，先检查全部目标行；有未到货行时应使用勾选验收。不能把缺金额行跳过后仍提示“整单成功”。

- 全部目标行校验通过后才一起入账；任意一行失败整批不入账，错误明确到物资行及字段。
- 提交中按钮禁用；结果未知时保留原输入、原正文与幂等键重试，不能换键重复记账。
- 版本冲突保留输入并要求重新核对，不自动用最新版本强行覆盖。
- 验收后保持当前单、筛选和选择上下文；未保存输入离开时提供“继续编辑／放弃修改”。
- 只有本次成功合格入库的逐件物资生成单件码；数量须整数，整批新增单件码遵守总量上限。按数量管理物资不生成逐件码。

## 5. 其他二三级页面如何简化

统一按任务大小选择呈现方式，不再让所有操作都变成全屏详情。

| 场景 | 推荐呈现 | 保留的保护 |
| --- | --- | --- |
| 验收数量、金额、库位、差异 | 当前行编辑／展开 | 行字段错误、位置权限与版本、并发保护 |
| 申报明细新增、修改 | 单内记录表就地录入，低频字段展开 | 普通人员草稿协作范围、提交后物资管理员修订及原因 |
| 物资名称、规格、分类、备注等短资料修改 | 信息库中适宽编辑区，保存后回原筛选位置；厂家仍属申报／验收批次 | 编码／ID稳定，有引用后单位与管理方式限制 |
| 领用 | 已知库存批次时直接带入；仅多批次才选择批次 | 申请与管理员发放分离，不能点“领用”就扣库存 |
| 期初／补录 | 库存页内单据工作区，Excel 导入与行录入共用记录表 | 补录原因、草稿核对、版本保护、一次确认记账及流水；重复文件须提示，当前导入追加草稿并非自动去重 |
| 分类、区域、库位、编号 | 物资设置内分区编辑，一次只显示一类 | 沿用实际支持的新增／停用／删除规则，不顺手扩大权限 |
| 历史验收、修订、流水 | 当前单或库存内只读展开；长内容再进入完整详情 | 历史快照、金额脱敏、返回上下文 |
| 标签设计、复杂化学资料、大单据 | 保留完整工作区并明确返回位置 | 现有纸型／旋转／校准、未保存保护，不能为减少层级删掉必要配置 |

长操作说明收进帮助，但错误、限制原因和提交结果必须常驻可见。每个工作区只保留一个主标题和一项主要提交动作，不将所有低频能力摆成多行工具条。

## 6. 代码与接口影响（待实施）

### 6.1 读取继续复用申报单

现有 `GET /api/materials/acceptance` 是**明细级分页**，不能先截取一页再前端分组，否则一张单会漏行、总数也错误。

建议扩展 `GET /api/materials/requests` 的验收进度筛选与按单统计，仍按申报单分页；选择后用已有 `GET /api/materials/requests/:id` 读取完整明细。`GET /api/materials/receipts?requestId=...` 提供历史。状态以服务端的合格量、结案量、剩余量为准，不根据屏幕可见行推断整单完成。

### 6.2 批量写入需要后端事务

现有 `POST /api/materials/receipts` 一次处理一行，而且成功会递增父单版本；首次关联资料也可能递增。因此**不能在前端循环调用单行 API 来冒充整单原子入库**，否则可能半单成功或第二行冲突。

建议新增 `POST /api/materials/requests/:id/receipts/batch`（拟定接口，当前不存在），提交父单版本、一个整批幂等键，以及各行版本、合格量、实际金额和可选差异字段。单行和批量复用抽出的事务内验收逻辑：

1. 同一事务先校验父单与全部行的初始版本、权限、剩余量、金额及资料。
2. 同一批次身份统一核对位置与位置版本。同批次不能在本次多行中指定不同库位；不能让第一行更新位置版本后将第二行误判为外部并发。
3. 资料匹配／建档、本次到货登记、验收事件及登记关联、库存流水、库位、单件码、审计和整批幂等结果一起提交或回滚。
4. 返回本次 `arrivalId`、全部成功事件与最终申报单；上传直接绑定该返回ID，不能通过重新查“最新到货”猜归属。失败返回行标识、字段和原因，不能只回“验收失败”。

可参考现有 `postOpening()` 的按批次归并、库位预校验与整批新码上限。库位目前属于“物资＋区域＋仓库＋批号＋效期”的库存批次整体，不是每瓶独立位置；页面不能画成已经支持逐瓶异位。

### 6.3 影响清单

| 范围 | 待修改点 |
| --- | --- |
| `src/public/material.js` | 三入口映射、按单验收状态、完整清单、行内差异、批量提交、历史与返回上下文 |
| `src/public/material.css`／`responsive.css`／`workspace.css` | 新布局覆盖层与短编辑范围，保留现有压缩前缀、同 DOM 和打印规则；不全站缩小所有 dialog |
| `src/public/material-scan.js`及导航调用者 | 扫码跳转接入新的验收／库存上下文，旧入口仍映射到真实页面 |
| `src/materials.js` | 按单筛选／统计、事务内验收复用、批量端点与错误结构、固定版本打印／深链接、到货清单及版本；保持角色＋操作权限及脱敏 |
| `src/schema.js`／迁移／严格备份恢复 | 到货登记与验收事件关联、厂家核对记录、清单版本和文件完整性；不能只补页面按钮 |
| `docs/MATERIAL_API.md`及使用文档 | 新读写合同、批量与重试、状态和入口说明 |
| 业务／前端／浏览器测试 | 分页、原子性、金额、并发、位置、编号、权限及实际响应式流程 |
| 发布准备 | 正式开发完成后再定业务版本，统一两份 YML、镜像、离线包与更新说明；本方案不更改0.13.1交付 |

优先复用现有申报、验收事件、文件存储和二维码生成能力，不另建重复业务账本。本次新增的到货登记关联及清单版本需要正式持久化设计、加法迁移和严格备份／恢复同步；它们目前不存在，不能只靠页面内存或附件文件名推断版本。

## 7. 实施顺序与验收

1. **入口重排与读取**：三主入口，设置分区，按单分页和完整明细；先验证旧功能仍能到达。
2. **原单核对与单行快捷验收**：保留Excel，补固定版本打印／下载和二维码登录后查看；相符行内金额／厂家／位置，差异展开、未关联补档，成功留在当前单。
3. **批量原子验收及到货清单**：服务端事务与整批幂等先完成，一次确认形成到货登记并关联各验收事件，再接分次清单上传／同次替换及其版本保护。不能先放前端循环按钮或直接覆盖旧文件。
4. **其余短操作**：申报明细、物资资料、领用和期初／补录按第5节逐页精简，复杂标签设计保留独立工作区。
5. **真实验收与交付**：临时 PostgreSQL 18、真实 API＋浏览器与既有回归通过后，再发布同版镜像和两份部署 YML。既有 R3/R4 仍是未完成计划，与本方案合并排期，不借本原型标记完成。

正式开发必须覆盖：

- 正常单填金额后原位入库，不弹普通二级表单；默认量为剩余量。
- 未填金额、0元无原因、拒收无原因、超剩余量均指到具体行，失败保留输入。
- 一批中第二行失败、建档失败、单件号冲突时整批回滚；重复点击／断网重试不重复入账。
- 两人同时验同单、跨行同批次库位、重复幂等键异正文等冲突不覆盖他人结果。
- 部分到货、拒收、结案、冲正保持原申报、历史与正确进度；已记账验收事实只读，仍保留有权限的受控修订、追加附件及符合条件的冲正，不将完成进度变成永久锁单。
- 普通人员查询物资、申请领用、物资管理员验收／发放、金额脱敏均按现有权限。
- Excel 导入导出、期初补录、扫码、二维码及打印入口可达；打印校准不回退。
- 打印申报单含厂家、空白勾选／实到数量／备注和固定版本二维码；扫码登录后查看对应原单版本，不跳到无关库存或默认替换成最新修订。
- 厂家相符可直接确认，不同须原因；原申报厂家不被验收实际值覆盖，后续库存／流水能追溯本次实到厂家。

## 9. 补充：纸质申报核对、厂家和分次到货清单

### 9.1 用户确认的实际流程

1. 物资管理员下载或打印已提交的申报单，纸面列出所有申报物资。
2. 第一次到货，在纸上勾选本次到货物资，记录数量与厂家；在系统选择本次到货行，填写实付金额，确认验收入库。

### 9.3 厂家是本次验收的核对项

验收清单常驻“申报厂家”和“实到厂家”，可与存放位置共用一列的上下两行，避免再扩大表格。原申报厂家是只读基准，实到厂家预填相符值；点击“验收入库”表示已核对本次数量、金额及厂家，不额外增加一组逐行确认弹窗。

- 申报已写厂家：实际相符直接确认；不相符在本行填写实际厂家和差异原因。
- 申报未指定厂家：明确显示“未指定”，填写实际厂家，不把“未指定”复制为真实厂家。
- 合格入库时厂家不能静默为空。实物确实未标明时，使用明确的“厂家未标明”状态及原因；它不是匹配成功，也不冒充任意厂家名称。
- 厂家属于申报／验收批次，不能改成整个物资信息库的唯一厂家，不改原申报值。实际厂家及核对差异保存在验收记录／快照中，与库存和流水关联。
- 同物资不同厂家分别记录，不能为了合并同类库存而丢失厂家来源。纯拒收保留能够核实的厂家及拒收原因，不为补一个未知厂家强行入库。

正式实现应在服务端校验并持久化核对状态、基准厂家、实际厂家与差异／未标明原因；不能只在前端显示“已核对”而不记录依据。新字段涉及迁移、API、Excel及严格备份恢复时一并同步。

### 9.4 上传与替换的页面行为

在验收单头放“上传本次到货清单”，本次验收成功后直接关联响应返回的登记ID，按钮旁显示该次编号与时间；历史中每次到货各有“上传／查看／替换”，重新进入时由用户明确选择归属。无到货登记时提示先核对并完成本次验收，避免上传成找不到归属的文件。一个到货登记可关联同次确认的多条验收事件，而不是给每条物资重复上传一份纸单。

上传在当前工作区的“到货清单”分区展开紧凑区域，提供“拍照”和“选择图片／扫描PDF”，不再打开一层完整业务页面。单头／成功提示的上传按钮直接切到该分区并带入确切到货ID；切回“办理验收”时收起资料区，保留待提交资料，避免上传条挤占验收表格。多页图片／PDF作为本次资料的一组文件，确认后一起成为新版本；拍照／选择完成还只是待上传，必须能取消、移除选错的页和重试。

手机拍照采用文件选择器的相机提示，是否直接进入后置相机由手机浏览器和系统决定；保留从相册／文件选择的入口。扫描件可由手机扫描工具生成后上传，不承诺直接控制USB扫描仪或自动OCR，识别文字或纸上勾选不能替代人工确认和服务器入账。

首版建议沿用当前**单文件5 MiB**上限，每版本最多10个文件且**整组原始文件合计不超过15 MiB**，允许JPEG、PNG及PDF；base64与元数据合并后仍须受现有总请求上限控制，不能误以为10个5 MiB文件可一次上传。文件过大或类型不支持时明确到文件名、实际大小、单文件／总量上限及可用格式。手机HEIC等未支持格式提示先转JPEG/PDF，不假装已转换。正式服务端须验证实际文件类型与大小，不能只信扩展名、浏览器accept或MIME；文件名只用于显示，存储继续使用随机标识。

同一次资料已有版本时，上传按钮明确写“替换本次清单”，填写原因；**新文件整组保存成功后才切换当前版本**。确认提交前取消、明确的文件校验失败或事务版本冲突保留旧版，不能先删旧文件再传新文件。提交后若响应丢失或用户中止等待，服务器可能已经保存；此时标记“结果待确认”，沿原正文及幂等键查证／重试，不能承诺仍为旧版，也不能换键盲目重传。默认只显示该次最新版，展开“历史版本”可查替换人、时间、原因和旧文件；历次到货分开排列，避免误认为前几次清单已经失效。

资料可稍后补传，显示“本次资料待补”；入库成功后资料上传失败要明确“入库已成功，清单待补”，重试只重传资料，不能重新提交验收。全部到货后仍允许按原权限补传／纠正资料。差缺结案须显示结案数量，不标成“所有物资已到货”。

### 9.5 后端最小扩展与不可破坏的边界

现有附件只关联申报或单条验收事件，验收附件仅追加、禁止移除；普通申报附件的读取权限又不同。因此本功能不能直接借普通申报附件保存含金额的验收扫描件，也不能覆盖既有验收文件的字节。

建议增加以下关联，仍复用现有文件随机存储及审计：

| 对象 | 保存内容与约束 |
| --- | --- |
| 到货登记 | 所属申报单、来源申报修订版、办理人／时间、本次验收事件集合；批量一次成功建立一个登记，单行也走同一模型，幂等重试不能多建轮次 |
| 清单资料版本 | 所属到货登记、递增版本、当前版本指针、上传人／时间、替换原因、该版本文件集合；历史不可被新上传改写 |
| 文件 | 原文件名、检测类型、字节大小、随机存储标识及摘要；每版独立保存文件，旧文件保留，不引入跨版本共享文件的去重模型 |
| 厂家核对 | 与本次验收事实关联的预期／实际及差异原因，原申报版本／快照保留 |

拟定读取／上传路径为 `GET /requests/:id/arrivals`、`GET /arrivals/:id/documents`、`POST /arrivals/:id/documents`，均是**待开发接口**。上传携带当前资料版本、幂等键、整组文件和替换原因；使用资料自己的并发版本，不因补拍照片改变父申报单业务revision。文件可先安全暂存，事务成功时一次切换资料版本；回滚清理本次新文件，成功提交前旧资料持续可读。

验收批量入口与第6节为同一个写操作，不再另建一套相同的入账API：成功结果追加到货登记及事件关联即可。现有附件归属有“申报／单行验收二选一”的数据库CHECK，新增资料版本归属必须扩展相应约束与外键。旧验收事件保持无轮次并标“历史逐行记录”，不按时间臆测到货批次，也不重记历史库存。

上传／替换沿用MATERIAL加验收操作权限；读取、预览、下载、历史文件及相关导出沿用验收附件的金额读取控制，不能只在页面藏按钮。无权者不返回文件名、预览或下载地址。单号二维码只负责定位原单，绝不绕过这些权限。备份／恢复必须包含到货登记、事件关联、资料当前指针、全部历史文件及摘要，拒绝跨单引用、缺文件或指针指向其他到货登记；旧schema备份按明确迁移规则补缺省，不把新schema强交旧程序恢复。

当前在线完整备份另有**附件总20 MiB／JSON总25 MiB**上限，分次照片及历史版本很快可能超限，不能宣称上述合法上传量都能在线导出。正式交付须说明并验证完整PostgreSQL18与附件运行目录的备份／恢复路径（保留一致性，不能直接复制正在写入的数据库目录），在线超限明确提示并转该路径，不能默默漏掉旧版照片或为让备份通过而删除历史。后续只有确实需要在线大备份时，再扩展归档流式导出。

# 物资管理：申报、验收与库存方案

日期：2026-10-17。以下保留方案与原型的设计历史；0.3.0已按用户指令接入正式业务、专表与页面，实际权限/接口和实施限制见 [物资API](MATERIAL_API.md) 与 [开发说明](DEVELOPMENT.md)。HTML仍是独立模拟原型，正式验证和发布状态以统一版本说明为准。

本次需求修订：用户新增“管理员创建物资分类、填报选择分类与归属”，并明确归属指**区域**；提交后改为**仅物资管理员可编辑**，替代初稿“所有角色永久禁止编辑”的规则。原提交版本仍保留，后续修改以修订形式留痕。

## 1. 建议采用的方案

在“物资管理”下设置 **物资申报、验收、库存** 三个主入口，贯通“多人填报 → 管理员提交 → 受控修订与分批验收 → 自动入库”的流程。历史申报单及修订版保留，库存可以追溯到期初登记或某次验收，不再将采购数量、到货数量当作库存相加。

继续使用当前 Node.js、SQLite WAL 和原生页面，先以单实例服务满足 10–30 人查询录入的目标，通过实测判断容量。这个人数是需求，不是已经通过的压测结果。无需为本轮工作更换框架或立即迁 PostgreSQL。

本轮只交付可行方案与 HTML 示例；下文的表、接口和权限均为待实现设计。现有生产页面、旧数据、版本号、镜像和发布标签保持原样。

## 2. 已确认需求与建议默认值

| 事项 | 用户已明确要求 | 本方案建议的补充规则 |
| --- | --- | --- |
| 三个入口 | 物资申报、验收、库存 | 进入物资管理默认打开申报；旧台账暂留“原台账”兼容入口 |
| 申报单 | 每次可新建表单，所有人可往表内增加物资 | “所有人”指所有登录账号；均可建单，只能改本人草稿明细；物资管理员可整理所有草稿明细 |
| 分类与归属 | 管理员可创建物资分类，填报时选择分类与归属区域 | 建议系统管理员 ADMIN、物资管理员 MATERIAL 均可维护分类/区域选项；普通用户只可选，区域与仓库、填报人分别保存 |
| 提交与编辑 | 仅物资管理员可提交；提交后仅物资管理员可修改编辑 | 普通用户只读；管理员填写修改原因，保留原提交版和前后差异，单据仍是已提交；不开放提交后新增/删除行 |
| 历史与导出 | 保留历史，方便查询和 Excel 导出 | 可区分原提交版和当前修订版；金额及导出单独授权，默认仅物资管理员；稳定用户 ID 判断明细创建者，区域不充当个人权限依据 |
| 验收 | 汇总历史申报，录入数量、金额，标记已验收 | 仅已提交明细可验收；物资管理员操作；支持分批，实际合格数量才入库 |
| 库存 | 支持期初库存，验收后增加，默认合并同类 | 建议在同物资、同仓库、同归属区域内合并，保留批次、有效期和来源流水；不同规格、单位或区域分别保留 |

上述补充规则用于把方案和示例做完整，尚不代表用户已经逐项确认。原型只演示主要路径，不以浏览器中的角色切换代替服务端授权。

## 3. 页面与业务流程

### 3.1 物资申报

列表显示申报单号、标题、创建人、创建日期、申报状态、明细条数、验收进度和提交人。支持按单号/标题/物资名称、日期、状态、填报人筛选；草稿与历史在同一入口查询，不到期删除。正文中的申报状态与验收进度分别显示。

新建申报单填写标题、说明、可选计划用途或期望到货日期。系统生成唯一单号。单号不使用“当前最大值 + 1”的非原子做法。

进入草稿后，全员可新增物资明细。每行至少包含：物资名称、**物资分类、归属区域**、规格型号、单位、申报数量、用途、填报人；另可填写品牌要求和备注。已有物资从主档选择，新物资先填完整属性，由物资管理员提交前确认或建立编码。填报人由会话确定，不接受前端指定别人的用户 ID；归属区域由用户从有效区域列表选择，不替代创建人和入库仓库。

管理员在申报入口的“分类与区域”中创建选项，例如分类“试剂、耗材、标准品”，区域“理化区、微生物区、公共区”；普通用户仅能在添加/编辑明细时选择，不能通过填报接口创建新分类或区域。名称去除首尾空白后非空、长度受限且不重复，保存稳定 ID。分类/区域不是个人授权范围；选用它们不改变明细创建者。首期管理只提供新增，不提供删除历史引用的操作。

同一申报单内，不自动合并不同人的申报行，以免丢失用途和责任归属；管理员可以查看按物资汇总的数量。普通用户编辑/删除本人草稿行，管理员编辑/删除草稿中的全部行。建单者可修改草稿标题、说明，管理员可统一整理；不允许普通建单者删除他人的明细。首期不提供整单物理删除。

物资管理员点击“提交申报”，查看最终清单并确认后，整单变为“已提交”，记录提交人和时间。空单、无效数量、未明确规格单位或未完成物资编码匹配时阻止提交。

**提交后普通用户只读，只有明确具有 MATERIAL 角色及提交后编辑权限者可修订。** 系统管理员若未兼任物资管理员，也不能编辑已提交单。原提交人、提交时间与原提交快照永久保留；修改不撤回草稿、不重新伪造提交，也不覆盖原版。

每次修改须填写原因，记录操作人、时间、版本、修改前后内容，递增单据修订号及明细版本。历史详情与导出应能区分原提交版和当前修订版。原型展示已有明细的修订，标题、说明和附件的受控修订在正式实现时接入相同机制。提交后暂不开放新增/删除行；遗漏物资另建补充单，避免编辑权限意外变成删除已入库来源的权限。

未产生任何验收/结案事件的行可修订分类、区域、物资字段及数量。已有验收记录的行仍可编辑分类、用途和申报数量，但编码/物资 ID、名称、规格、单位、仓库和归属区域受到保护，不能直接改变已经入账的物资身份；填报人不因修订改变。数量下限为**有效已验收量 + 有效结案量**，管理员增加数量只增加待验余量，减少数量只减少待验余量，均不自动增减库存或金额。需要更正验收事实时使用独立冲正流程，不能用修改申报代替。

### 3.2 验收

默认显示所有历史已提交申报单中尚未完成的明细；可切换“全部/未验收/部分验收/已验收/差缺结案”，按原单号、物资、日期查询，并进入原申报单详情。普通用户只读，物资管理员按上述修订规则编辑。

每次验收填写：本次实际合格数量、本批含税总金额（元）、验收日期、仓库/库位、操作人；试剂和标准品按物资要求填写批号、有效期、证书信息，耗材可选填。金额明确为**本次合格入库部分的总金额**，单价由金额÷数量显示，不把单价与总额混用。可记录不合格数量、原因和附件；不合格部分不入正常库存。

例如申报 10 盒，第一次合格到货 6 盒、总额 720 元：本次入库 +6 盒、+720 元，标记“部分验收 6/10”；第二次验收 4 盒后标记“已验收 10/10”。两次价格可以不同，库存仍合并为同一物资，批次和各次金额分别保留。

规则如下：

- 合格数量必须大于 0，累计有效合格数量不超过**当前修订版申报数量**减去有效结案数量。需要增加采购量时由物资管理员先修订申报并记录原因，重新确认验收依据，不能直接超量入库。
- 正常验收金额大于 0；赠品等零金额情况须明确选择零金额原因。拒绝负数、非有限数、超过精度或安全整数范围的数据。
- 分批到货每次新增验收记录，不能覆盖上次验收。界面展示历次验收人、时间、数量、金额和库存流水链接。
- 不合格/拒收仅登记异常，不抵扣未来允许合格验收的数量，也不增加库存；换货合格后再验收。若同次有合格与拒收部分，记录各自数量，合格+拒收数量不超过当时剩余待处理量，不能重复计算合格量。此处采用“拒收不关闭申报余量”的建议规则，需与实际退换货习惯一起评审。
- 确定余量不再采购时，管理员填写原因执行“差缺结案”，追加结案事件，关闭剩余量，不改原申报数量；“差缺结案”不冒充“全部已验收”。普通验收和结案事件分开记录。
- 已记账的验收不能直接编辑、删除或再次入库。录错时通过关联原验收的冲正流水纠正，再重新验收；首期只支持整笔冲正，数量金额精确反向，原验收最多冲正一次，并以唯一约束防止不同请求号重复冲正。冲正必须事务化回退数量和金额、保留审计，已被出库占用的数量不能直接冲减。正式上线必须具备这种纠错路径，原型暂只演示正向验收。

“已验收”按累计有效合格数量与当前修订数量计算；单据的“未验收/部分验收/全部验收/差缺结案”由各行结果汇总，不提供手工勾选后直接改状态的入口。已全部验收行增加申报量后重新显示“部分验收”，已入库数量与金额不变。每次验收保存当时物资、分类、区域、单位、仓库及申报修订号的快照，不能重新用当前申报内容解释历史验收。

### 3.3 库存

列表显示物资编码、名称、规格、单位、仓库、**归属区域**、现存数量、库存金额（需权限）、最近入库日期；详情显示批次/有效期、期初登记和每次验收流水及来源单据。默认汇总展示，批次详情保留，不因汇总而覆盖批号。

**建议同类合并规则：物资主档 ID + 仓库 ID + 归属区域 ID。** 主档编码唯一且稳定，名称、类型、品牌/等级、规格、基本单位共同确认物资身份。示例中用“物资编码 + 规格 + 单位 + 仓库 + 归属区域”直观展示该规则；正式系统规格和单位属于主档，不能通过任意输入改变同一编码的含义。归属是区域已获用户确认；不同区域库存分开是保护归属的建议默认值，不把它冒充用户明确要求。分类仅用于检索，不作为库存合并键。

| 情况 | 处理 |
| --- | --- |
| 同一物资、同规格单位、同仓库及区域，不同供应商/价格/批次 | 汇总到同一库存行，验收和批次流水分别保留 |
| 同名但规格、纯度、等级、品牌要求或单位不同 | 建立不同物资编码，不按名称相同自动合并 |
| 同一物资，不同仓库 | 分开余额，可在页面汇总总量 |
| 同一物资同仓库，不同归属区域 | 分开余额，不能合并后丢失归属；后续转移区域应走独立调拨，不直接改申报 |
| 新物资尚无库存 | 第一次合格验收时自动新建余额，不要求先登记空库存 |
| 采购用“箱”，库存用“盒” | 首期不自动换算；提交前统一基本单位，不猜换算比例 |

期初库存由物资管理员逐项登记物资、分类、归属区域、仓库、数量、期初总金额、基准日期及批次信息，生成“期初”流水。建议切换日统一盘点，旧台账核对后一次导入，开始验收后关闭初始化入口。重复导入同一来源必须拒绝或幂等返回；后续遗漏按有原因的调整流程处理，不再直接覆盖余额。

在本次新增流程范围内，`现存数量 = 期初数量 + 有效验收入库数量 + 调整净量`，金额同理。接入旧出库功能前必须增加事务化出库流水，并扩展为扣减出库；当前旧出库记录仅是普通台账，不能声称已经同步扣库存。首期新库存不能继续接受旧“直接修改当前库存”的入口写入。

库存数量不跨单位直接相加成一个总数；概览优先显示“物资品种数、待验收行数、库存预警数”。金额可汇总，数量需按同物资同单位查看。

## 4. 权限建议

账号可以兼任多个角色。“仅物资管理员可提交和编辑已提交单”按明确业务角色处理：系统管理员若需要这些业务操作，须另兼任 `MATERIAL`，不能因为已有 `*` 权限就自动绕过限制。分类/区域维护建议允许 `ADMIN` 或 `MATERIAL`，不因此额外获得已提交单编辑权。

| 操作 | 普通登录用户 | 物资管理员 MATERIAL | 仅系统管理员 ADMIN |
| --- | --- | --- | --- |
| 新建申报单、添加物资 | 可以 | 可以 | 可以 |
| 修改草稿 | 本人明细；本人创建单的标题/说明 | 所有草稿 | 与普通用户相同 |
| 创建分类、维护区域选项 | 不可以，仅选择 | 可以，需维护权限 | 可以，需维护权限 |
| 编辑已提交申报 | 不可以，即使是本人行 | 可以，需专用编辑权限、原因与修订记录 | 不可以，需兼任 MATERIAL |
| 已提交单新增/删除行 | 不可以 | 首期不开放 | 不可以 |
| 查看申报历史及原始明细 | 可以 | 可以 | 可以 |
| 提交申报、验收、结案、冲正 | 不可以 | 可以，另需对应操作权限 | 不可以，需兼任 MATERIAL |
| 查看库存数量 | 可以（建议默认） | 可以 | 可以 |
| 查看实际金额、导出 Excel | 默认不开放，可另行授权 | 默认开放 | 按金额及导出权限授权 |
| 期初导入/登记、库存纠错 | 不可以 | 可以，需对应操作权限 | 不可以，需兼任 MATERIAL |
| 账号与角色分配 | 不改变现有规则 | 不额外获得 | 沿用系统管理权限 |

申报入口应为所有已登录账号开放，包括当前缺少 `materials.read` 的财务角色；不能为了填报而授予全员现有的 `materials.write`。正式实现可增加 `materials.request.submit`、`materials.request.edit_submitted`、`materials.acceptance.write`、`materials.stock.initialize`、`materials.stock.adjust`、`materials.categories.write`、`materials.regions.write`、`materials.amount.read`、`materials.export` 等动作权限，前五项同时要求有效 `MATERIAL` 角色；分类/区域维护同时要求 `ADMIN` 或 `MATERIAL`。全员填报/本人草稿编辑通过认证、创建者 ID 和状态约束，不能用业务归属区域代替身份判断。

每次请求重新查角色与权限；隐藏按钮仅改善界面，不能作为授权。金额字段需在服务端响应中裁剪，并覆盖查询、详情、导出、总额、仪表盘等路径，不能只在页面隐藏。完整物资备份同时要求备份权限与金额读取权限；金额被裁剪的文件仅是部分导出，不得标为完整备份或用于库存灾备恢复。恢复仍按独立管理权限控制，恢复权不等于普通业务编辑权。

## 5. 结合现有项目的最小实现

### 5.1 当前差距

- `src/public/material.js` 目前有采购、验收、入库、出库等 16 个分类入口，统一从 `records` 按 JSON 字段筛选。现有“库存”筛选还包含同类型的其他流程记录，不是真实库存余额。
- `src/server.js` 的通用记录 API 有 `version` 乐观锁，但没有申报单与明细关系、提交后受控修订、分类/区域字典、分批验收与入库事务；可手填的 `owner` 不能用于本人权限判断。
- 多个角色已有 `materials.write`，`ADMIN` 的 `*` 会直接放行；这些不能满足本方案的业务权限。
- 当前物资前端导出 CSV，通用 `/api/export` 导出 JSON，**尚无真正的 `.xlsx` 导出**。现有备份只覆盖原表，增加专表后需同步扩展。

### 5.2 数据结构建议

保留原 `records`，新闭环采用八张专表（初稿五张，本次为分类、区域和修订历史增加三张），避免用可任意改动的 JSON 状态表示权威库存。沿用当前 SQLite、参数化查询和审计，新增必要约束与索引，不建立新的框架层。

| 表（建议名称） | 最少职责与关键字段 |
| --- | --- |
| `material_categories` | 稳定分类 ID、唯一名称、创建人及时间；普通填报只引用有效 ID，不提供历史引用删除 |
| `material_regions` | 稳定区域 ID、唯一名称、创建人及时间；独立于仓库和用户身份 |
| `material_catalog` | 稳定 ID、唯一编码、默认分类 ID、名称、品牌/等级、规格、单位、是否启用；被单据引用后不直接改规格/单位 |
| `material_requests` | 唯一单号、标题、说明、草稿/已提交、创建人 ID、原提交人/时间、头版本、内容修订号、原提交快照、提交后的修订版号、可选关联原单 ID |
| `material_request_items` | 所属单、物资 ID、名称/规格/单位快照、分类 ID、归属区域 ID、仓库、申报数量、用途、填报人 ID、明细版本；保留当前修订内容 |
| `material_request_revisions` | 所属单、唯一修订版号、明细 ID（表头变更可为空）、完整前后快照、原因、操作人及时间；只追加，原版不覆盖 |
| `material_receipts` | 每次事件类型（验收/结案/冲正）、申报行与修订号、当时的物资/分类/区域/仓库快照、有效合格数量、拒收/结案数量、总金额、批号/有效期、原因、原事件 ID、操作人、时间、唯一请求号；原验收的冲正引用唯一 |
| `material_stock_movements` | 期初/验收/冲正/调整来源、正负数量金额、物资/仓库/归属区域和当时快照、批号/有效期、操作者与原因；来源唯一约束防重复记账 |

仓库先使用受控的默认仓库和稳定仓库代码，不新增复杂仓储管理。库存余额按物资 ID + 仓库 ID + 区域 ID 汇总有效流水计算，先不维护第二份余额表；批次明细按批号和有效期进一步分组。新物资的第一条流水自然生成新的库存汇总行。原提交快照、每次修订和验收快照分别保留，之后修改当前申报不改历史申报版本或历史入库解释。验收、冲正和期初来源可追溯；已入账流水及修订记录只追加，不能物理删除，不能依赖可清理的通用审计日志保存唯一修订正文。新专表不挂通用 `/api/records` 写接口，通用恢复也不能把伪造 `records.data` 变成新库存。

开启并验证外键约束，增加唯一约束，以及申报单日期/状态、申报行所属单、修订所属单/版本、验收所属行、库存流水物资/仓库/区域及来源索引；分类、区域 ID 必须存在，普通用户不能提交字典新建请求。可能扣减库存的操作在写事务内检查汇总余额非负。数量最多三位小数，数据库以千分单位整数保存；金额以分整数保存。API 接收十进制字符串后严格解析，不能先用浮点四舍五入掩盖超精度。检查数量、金额和累加结果的范围；显示单价只作展示，记账依据始终是总金额。

### 5.3 接口与事务

建议单独使用 `/api/materials/categories`、`/regions`、`/requests`、`/requests/:id/items`、`/requests/:id/submit`、`/requests/:id/revisions`、`/receipts`、`/stock`、`/stock/opening`、`/stock/movements`、`/export.xlsx` 等资源与动作（均在 `/api/materials` 下），前端不再通过通用记录编辑器修改新单据。已有响应/会话/错误与审计函数可以复用。

**多人填报：** 新增/修改/删除明细都在短事务内检查父单仍为草稿。编辑已有行携带该行版本；写成功递增明细版本及父单内容修订号。标题、说明、附件等所有影响提交快照的内容变化也必须递增父单内容修订号。不同人增加不同明细不互相覆盖，同一行冲突返回 409，保留输入并允许重新读取。

**整单提交：** 管理员预览后提交所见内容修订号；事务内重新检查登录角色、草稿状态、修订号和全部明细，保存不可覆盖的原提交快照，初始化提交修订版为 1。如果预览后有人新增或修改，提交返回 409 并要求重新预览，不能静默提交管理员没看到的新内容。提交与最后一次草稿编辑同时发生时，只能“草稿编辑先完成、提交重新预览”或“提交先完成、原草稿保存被拒绝”；物资管理员也需重新读取已提交版，再填写修订原因。

**提交后修订：** 专用写事务重新核对 MATERIAL 与编辑权限、已提交状态、父单/明细版本、当前有效验收量和结案量，校验原因及受保护字段，再追加修订快照、保存当前内容、递增版本并写审计，一次提交。编辑与删除分开授权，不能复用一个放宽的 `canEdit` 判断而误开放删除。验收窗口打开后若申报已修订，验收请求必须按所见父单/明细版本返回 409 并重新确认；修订窗口打开后若已有新增验收，修订保存同样重新校验，不按旧的可编辑字段或数量下限强行写入。

**验收入库：** 在同一事务中检查角色、父单已提交、所见修订号与明细版本、剩余数量、请求号和输入，新增带入账快照的验收、写唯一来源的库存流水并记审计，然后统一提交。库存从这些流水汇总，不在前端先查余额再覆盖。任一步失败回滚，不能出现验收成功但库存没增加。合格数量条件在事务内检查，不接受前端传来的剩余数量或状态作为依据。

每个记账动作带唯一幂等请求号（与操作者绑定，并保存请求摘要）；网络重试用同号同内容返回原结果，不再次入库，同号不同内容拒绝。不同请求号对同一行同时验收仍需事务内校验累计量，不能只靠按钮禁用。剩余 10 时两人各验收 6，只能一个成功，另一个整笔冲突，不能留下部分入账。有限写锁等待和失败提示，不无限重试。继续单实例 SQLite，事务内不做上传、Excel 生成或外网调用。

旧通用记录、旧 CSV/JSON 导出、回收站、附件、数据恢复与直接 CRUD 不得成为绕过提交后业务编辑权限、修订记录或直接改新库存的旁路；正式实现时逐项核查。历史附件也需要专用关联，提交后的附件修订同样仅允许物资管理员说明原因并保留旧版本，验收附件单独归属验收事件。

### 5.4 Excel、迁移与备份

- 正式导出生成真正 `.xlsx`，建议包含“申报单信息、申报明细、修订记录、验收流水”工作表；分类、区域和版本明确输出，可选择原提交版或当前修订版，库存独立导出。单单导出与按日期/状态筛选导出使用相同授权和数据范围，标记导出时间与草稿/已提交状态。金额字段依授权决定是否包含。
- 使用维护中的成熟 XLSX 库并锁定版本，不手写一套 Office 打包协议。数量、金额写为数字，编码、备注等写为文本，不把用户输入当作公式或超链接；不能把 CSV 改扩展名伪装成 Excel。分页读取并限制一次导出规模，避免同步大文件阻塞查询。
- 第一次上线先停服备份整个运行目录，在副本迁移。旧台账保持只读查询，不自动把所有采购/入库记录累加为库存；管理员核对盘点后明确导入期初，保存旧记录到新物资的映射与导入批次，防重复。
- 版本化迁移新增专表，不删除旧表。新备份格式增加上述专表、分类/区域 ID、原提交与修订历史、验收快照、用户 ID 映射和附件关联；恢复在独立空目录验证外键、唯一来源及余额与流水对账。不得用现有“追加导入”直接重放记账流水；重复恢复必须拒绝或使用明确的幂等迁移。
- 回退代码不能自动回退数据库；上线前保留可恢复的完整副本。新版本运行/构建目录按现有约定隔离，不覆盖 rc.5 的镜像、标签或缓存产物。Docker 版本号在正式实现与验收后再定。

## 6. 建议开发顺序与完成标准

| 顺序 | 开发内容 | 必须看见的结果 |
| --- | --- | --- |
| 1 | 专表迁移、分类/区域管理、业务权限、申报与受控修订 | 全员选择分类/区域填报；仅物资管理员编辑已提交单，原因及原版可追溯，接口不能绕过 |
| 2 | 物资主档、期初登记、分批验收、库存与冲正事务 | 一次验收只入库一次；同类正确合并；余量、金额、批次与流水可对账 |
| 3 | 正式 XLSX、历史筛选、附件与完整备份恢复 | 导出可由 Excel 正常打开；恢复后数量金额一致，权限和关联不丢失 |
| 4 | 并发与浏览器角色验收，再制作新版 Docker/YML | 多人填报和同时记账无丢失/重复；旧版本、旧数据与新版本隔离 |

首期至少验收：

1. 财务等原本没有物资读权限的登录账号也能进入申报并加行；未登录不可访问；不能伪造填报人。
2. 两人同时在同一草稿加行都保留；同一行版本冲突；普通用户改他人草稿行、编辑任何已提交行、提交单据、调用验收接口均被拒绝；ADMIN 无 MATERIAL 不得编辑已提交单。
3. 管理员预览后有人加行时提交失败；提交与草稿保存竞争只有一种合法顺序。物资管理员提交后编辑必须有原因并递增版本，原提交快照和全部修订保留；不能通过普通 CRUD、删除、附件或恢复绕过。
4. 分两次验收 6+4=10，进度正确；合格/拒收分开；11 超量、负数、超精度、过大数量/金额被拒绝；零金额须有原因。
5. 同一请求重复提交只入库一次；两个不同请求并发验收不能超量；故障回滚后验收、流水、余额均保持一致。
6. 同物资同仓库同区域合并，不同规格单位、仓库或区域分开，价格不同可合并，批次仍可追溯；新物资自动建余额。
7. 期初重复导入被阻止；差缺结案不标为全部验收；冲正记录保留且数量金额回退一致；余额与流水对账。
8. 真正 XLSX 可打开，文本以 `=` 等字符开头不会变公式，普通用户不能经详情/汇总/导出读到未授权金额。
9. 用隔离运行目录进行备份恢复和旧库迁移；接近实际数据量的 30 用户查询、明细保存、提交、验收和导出混合测试，记录延迟、错误率、写锁及数据一致性。
10. ADMIN/MATERIAL 可新增分类/区域，普通用户仅能选择有效 ID；重复名、空白名、超长名及伪造 ID 被拒绝，名称不会被当作 HTML 执行；所有选择与明细归属正确显示。
11. 申报修订后已入库数量金额不变；数量小于有效已验收+结案量被拒绝；已有验收行改物资身份、规格单位、仓库或区域被拒绝。已全部验收行扩量后变为部分验收，后续验收引用新修订版，历史验收仍引用旧快照。
12. 编辑和验收窗口交叉打开时，旧版本保存返回冲突；提交后修改按钮不能连带开放新增/删除行，取消修改不留修订；导出原版/新版与备份恢复都保留分类、区域和修订关系。
